# disflow 设计 v0.1 —— 分发器 · 树 · 图

> 状态：**设计（未实现）** · 2026-10-10
> 输入：用户口述需求 + fat3 仓内先例实测（flowcore / kaa / automation-lifecycle）
> 本文件是本线的**唯一落点**。

---

## 0. 一句话

**用一棵树提供上下文继承，用一张图提供调度与引用，配一个确定性分发器（只推不跑）按阶段把就绪任务派给短命 worker。**

---

## 1. 需求收敛（先回答“到底要解决什么”）

用户原话要点：

1. 参考任务的分发模式，先用 **dispatch 模式**。
2. 相当于**看板**，多个看板串成工作流：有的看板完成需求、有的完成设计、有的完成开发。
3. “看板”不一定是真看板，可能是**树形结构**；读取的人去树上看看有没有待完成的任务。
4. 待答问题：**多个保活 agent 抢任务，还是用一个 dispatch 分发器调用 agent？**
5. 为什么用树：**树有组织结构和上下关系，任务能拿到背景信息等一系列信息**。
6. 光有树不够，要结合 **Graph 模式**：
   - ① 用合理的树组织**基本信息框架**；
   - ② 通过 Graph 关联**相关的任务**。

三问（为什么做 / 给谁做 / 判据）：

| 问 | 答 |
| --- | --- |
| 为什么做 | 把“人肉盯多个 agent/多个看板做协调”变成**可复现的调度**：任务一就绪就被派发，上下文自带，不重复劳动，可断点续跑。 |
| 给谁做 | **编排者**（人 / 父 agent）与控制循环；**worker**（短命执行者）。二者通过同一份事实源交互。 |
| 判据 | ① 就绪任务能被确定性算出；② worker 上下文从树祖先链注入，无需人工拼背景；③ 并发不重复劳动、不写冲突；④ 崩溃后可重建、可续跑。 |

## 2. 先回答那个二选一：保活 agent vs 分发器

### 2.1 结论

**用分发器。** 保活只允许出现在**进程池层**（复用进程资源），不允许出现在**决策/上下文层**。

> 关键区分：**保活的是进程（资源），不是 agent 的上下文（决策者）。**
> 每个任务开一个**新上下文**（fresh context），背景从树的祖先链注入；执行完即回收。

### 2.2 对比

| 维度 | 多保活 agent（各自轮询/抢任务） | 分发器（单调度者 + 短命 worker） |
| --- | --- | --- |
| 就绪判断 | 每个 LLM 各自“看树判断我该不该拿” → 不确定、不可复现 | 纯确定性函数 `ready(n)`，可单测、可 dry-run |
| 上下文 | 常驻上下文会漂移/污染，且互相看不到边界 | 每任务 fresh，从祖先链注入，边界清晰 |
| 成本 | N 个 agent 空转烧 token / 占会话 | 按需 spawn，空闲即零 |
| 并发正确性 | 并发 claim 同一节点 → 必须锁 + 租约（kaa 已为此上 `flock`） | 决策串行化，worker 只执行，天然不打架 |
| 失败域 | 一个 agent 崩了要重启、丢状态 | worker 崩了只影响该任务，状态在事件流里 |
| 可观测 | 分散在各 agent 的会话里 | 派发计划是一份可读产物 |
| 延迟 | 任务一出现立刻接（低延迟） | 有调度间隔/触发开销 |

**保活什么时候才对：** 超高频小任务、需要**共享连续会话记忆**的任务。
即使这样，正确形态也是「**一个分发器 + 一个常驻进程池**」——池子复用进程，分发器仍是唯一决策者；
而不是「N 个 agent 各自扫树抢活」。

### 2.3 与 fat3 先例一致

kaa 已把这条判据固化：

- `kaa drive` / `flowcore` 的 `TreeRuntime.drive` 明说 **“只推不跑”**：引擎算出该派谁、怎么派，**spawn 归宿主**。
- `kaa handoff brief|collect` 是**派发协议，不是执行器**（谁 spawn 归宿主）。
- `kaa supervise` 明说 **“一次性观察，立即返回，不做常驻”**。
- `job submit|wait|collect` = 异步提交即返回 + **回收不跳验证** + 租约串行。

⇒ 本设计不发明新范式，只是**把已有的“只推不跑分发器”补上依赖图那一层**。

## 3. 树 + 图：各管一段（核心判据）

用户要树也要图。**不要混用，否则两头都坏。** 分工：

| | 树（Tree） | 图（Graph） |
| --- | --- | --- |
| 边 | `parent_of`（结构归属，**单父**） | `depends_on` / `relates_to` / `produces` / `consumes` |
| 管什么 | **上下文继承** | **调度与引用** |
| 读什么 | 祖先链 root→…→node 的声明字段 | 入边依赖是否满足、横切引用 |
| 约束 | 无环天然成立（唯一路径） | **调度边必须 DAG**；引用边可成环 |
| 数据量 | 有限、沿路径 | 任意、需去重 |

**判据一句话：归属关系进树，引用/时序关系进图。**

### 3.1 为什么上下文不能走图（反例）

如果“背景信息”也靠图来递归收集：

- 引用边可成环 → 上下文收集会**死循环**；
- 一个节点可能有多条到达路径 → 收集结果**不唯一、不可复现**；
- 深链会**指数膨胀** token。

树保证“唯一祖先链 + 有限深度”，所以**上下文继承只走树**。

### 3.2 为什么调度不能只走树（反例）

- 跨子树的依赖（A 分支的产物被 B 分支消费）——树表达不了；
- 横向产出物依赖（`produces/consumes`，kaa registry 已实测）。
  ⇒ **依赖边必须进图**。

### 3.3 组合后的形状

```text
                 [ root: 目标 ]
                  /          \            ← 树边：上下文继承
        [ 需求/board ]     [ 设计/board ]
            |    \            |
       [dev]  [dev]      [dev]
            \    |           /
             └───┴───┬──────┘              ← 图边：depends_on / relates_to
                 [ verify ]
```

- **上下文注入**只走竖直的树边；
- **就绪判断 / 横向关联**走水平的图边。

## 4. 看板是一等实体（目标；当前实现为视图）

> **2026-10-11 定位已升级**（[ADR 0005](decisions/0005-看板提升为一等实体.md)）：看板从「视图」升为**一等实体**
> （固定列结构 + 挂在其上的分发器/验收器），树/图是板内维度。本节为**目标设计草案**，实现仍是视图形态。

用户说的“看板”（需求 / 设计 / 开发）本质是**阶段（stage）**。
**工作流模板 = 阶段图**（需求 → 设计 → 开发 → 验证），实例化后每个节点带 `stage` 字段。

- 看板视图 = 按 `stage` 过滤/分组**同一棵树**的投影；
- 树视图 = 按 `parent` 缩进；
- 图视图 = 按边展开。

> **三种视图，一份事实源。** 绝不建“看板表 + 树表”双写——那双源立刻会漂移
> （fat3 已有教训：第二份事实、手工清单、层叠修补，见 kaa §1.2“宿主侧去补丁三批”）。

## 5. 数据模型（草案）

### 5.1 节点

```jsonc
{
  "id": "n7",
  "parent": "n2",              // 树边（单父）
  "stage": "design",           // 看板/阶段
  "mode": "decompose",         // 本型（决定开工模板/门）
  "status": "pending",         // pending|running|done|failed|skipped
  "goal": "…",                 // 本节点目标（可追溯父目标）
  "context_fields": {          // 供后代继承的声明字段
    "constraints": ["…"],
    "background": "…"
  },
  "depends_on": ["n4"],        // 图边（调度；必须 DAG）
  "relates_to": ["n9"],        // 图边（软引用；可成环、不影响就绪）
  "produces": ["parser"],      // 图边（产出物）
  "consumes": ["schema_v2"],   // 图边（产出物）
  "touches": ["src/a.py"]      // 写面（派发期冲突检测）
}
```

### 5.2 就绪判据（唯一函数 `ready(n)`，纯确定性）

```text
ready(n) := status(n) == pending
          ∧ (n 是容器 → 其子节点已满足展开条件；n 是叶子 → true)
          ∧ ∀ d ∈ depends_on(n): status(d) == done          # 图入边
          ∧ 未被租约占用（无 running 的 holder）
          ∧ 本波内 touches 无交集                              # 写面不重叠
```

`ready` 是**单源真相**：分发器（push）和 worker（pull，即用户说的“去树上看看有没有待完成的”）
**调同一个函数**——两面不分叉（延续 `drive` 的 `ready_wave` 与人类面同源约定）。

### 5.3 上下文投影

```text
context(n) := 祖先链上各节点的 context_fields（root→…→parent）

            ⊕ { 每个 depends_on 前置节点的产物摘要 }

            ⊕ relates_to 引用（只给指针，不递归展开）
```

- 前两段**沿树唯一、有限**；
- 第三段只给引用句柄，避免图膨胀。

## 6. 分发器架构

### 6.1 组件

| 组件 | 职责 | 关键约束 |
| --- | --- | --- |
| **事件流** `events.jsonl` | 唯一真相 | append-only |
| **投影** `state.json` | 由事件重建 | 原子刷新；可从事件 rebuild |
| **分发器** `devflow drive` | 算 `ready_wave` + 每步建议 | **只推不跑**；输出机器可读 JSON + 人类可读文本（同源） |
| **派发协议** `devflow handoff brief\|collect` | 写全 brief / 校验结果契约 | **不写 node-done**（验证仍归门） |
| **门** `devflow done` | 跑验收 → 通过/拒收 | 证据元数据自算，不手抄 |
| **worker** | 短命执行者 | spawn 归宿主；写完交结果即退 |

### 6.2 生命周期

```text
drive（算就绪）→ handoff brief（写契约）→ [宿主 spawn worker]
     → worker 执行 → handoff collect（校验结果，落盘）
     → done（跑门）→ 通过 → 事件入流 → drive 重算
```

### 6.3 并发

- **单写者收口**：同一文件 / 门配置 / 部署树由**单一写者**收口；
- **租约 + `flock` 真互斥**（kaa 1.2 已把“重读终态”的窗口收窄补丁替换为真锁）；
- **同波写面校验**：`touches` 重叠者自动排队（`flowcore.drive` 已提示 `--touches`）。

### 6.4 不做常驻

无 daemon。触发方式沿用 `automation-lifecycle` 的三选一：
外部 cron / 事件驱动 / 主动维护——**分发器本身不常驻**。

## 7. 与先例的关系：复用还是重造

**优先复用 fat3 的 `flowcore`，把 disflow 做成它的一个实例（spec + reducer + gates），只补“图”那一层。**

| 能力 | 现状 | disflow 要做什么 |
| --- | --- | --- |
| 存储/投影 | `flowcore.store` 已有 | 直接用（注入 reducer） |
| 状态机 | `flowcore.fsm` 已有 | 直接用（注入 status_gate 表） |
| 门引擎 | `flowcore.gates` 已有 | 直接用（注入门谓词） |
| 树/分发面 | `flowcore.tree.TreeRuntime.drive` 已有，“只推不跑” | 直接用 |
| **依赖图** | **缺**——`ready_siblings` 只按 `(parent, phase)` 分组，**投影里没有依赖字段** | **补 `depends_on`/`relates_to` 边 + `ready(n)` 的图入边判据 + 环检测** |
| 语言中立 | `check-flowcore-neutrality.py` 守 | 保住：lib 不出现业务名词 |

若要与 fat3 彻底解耦，则把 `scripts/flowcore/` **fork 到本仓**，但保持同样的公开 API。
决策点：**先复用还是先 fork** —— 见 §9 未决。

## 8. 不做什么（边界）

- **不建 daemon**：无常驻服务，文件式 + 按需触发。
- **不做“看板 + 树”双写**：看板只是投影。
- **不让 LLM 算就绪**：就绪/依赖/波次是确定性逻辑，交引擎。
- **不在图上做上下文递归**：上下文只走树。
- **不让 worker 自己写 `done`**：结果落盘与验证分离（门是唯一放行者）。

## 9. 未决问题（下一步）

1. **依赖边存哪**：写进节点 `depends_on`（简单、随节点投影）vs 独立 `edges` 集合（便于图查询）。
   倾向：节点内声明 → 投影时派生邻接表（避免双存）。
2. **环检测时机**：`expand`/`add-edge` 时立即拒绝（fail-fast），还是 `drive` 前统一校验？
   倾向：写时即拒（与 kaa registry 的拓扑序登记同理）。
3. **`relates_to` 的传递性**：只一跳还是可配置深度？（影响上下文膨胀）
4. **多写者收口**：跨仓/跨 worktree 时写面如何声明与仲裁。
5. **POC 范围**：先做“树 + `depends_on` + `drive`”最小闭环，验证 `ready(n)` 在真实任务上不误判、不漏派。
6. **复用 vs fork flowcore**（§7）。
7. **是否 `git init`**：本仓当前非 git 仓，而一致性门依赖 git；落地前确认。
