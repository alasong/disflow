# 0013 NFR-3 / FR-16 的边界：禁「常驻」而非禁「入口」

- **Status**：Active
- **Date**：2026-10-11
- **关联**：[0011](0011-web入口-实现.md) 交付了 `disflow/web.py`（本地 web 入口）；
  本篇解决它与 NFR-3 / FR-16 的冲突。

## Context

`disflow/web.py` 落地后，**收尾门立刻报红**（机检 30 → 失败 2）：

```text
FAIL: [FR-16] 引擎不内置常驻进程
FAIL: [NFR-3] 文件式：无服务、无数据库
```

**这不是误报**，是真冲突。两条需求的原文与机检实现：

| 需求 | 原文 | 机检实现（改前） |
| --- | --- | --- |
| NFR-3 | 「文件式：无服务、无数据库；运行产物与源码分离」 | `git grep` 黑名单：`http\.server\|socketserver\|sqlite3\|flask\|fastapi\|django\|\.db` |
| FR-16 | 「spawn 归宿主；引擎不内置常驻进程」 | `git grep`：`daemon\|threading\|multiprocessing\|while True` |

`web.py` 用了 `http.server` + `ThreadingHTTPServer` ⇒ **两处都命中**。

**问题在于判据的粒度，不是功能本身**：

1. **NFR-3 的语义在上下文里很清楚**：它在 NFR 组（零依赖 / 语言中立 / 可测试 / 可断点续跑 /
   规模预算 / 不静默降级）里，与「无数据库」「运行产物与源码分离」并列 —— 管的是**数据与运行
   形态**（文件式 vs 服务式/DB 式）。而机检把它实现成了**符号黑名单**，等于把形态约束做成
   了「不许出现某些字符串」。
2. **FR-16 禁的是「常驻」**，`web.py` 是**按需启停的本地入口**（`python3 -m disflow.web` 才起，
   Ctrl-C 即停，进程结束服务即止）—— 与引擎自己起并保活的 daemon 是两件事。
   而机检禁 `threading`，连标准库自带的请求并发实现一起禁了（`ThreadingHTTPServer` 不产生
   常驻后台线程池）。
3. **NFR-3 全仓没有任何 ADR 或设计文档解释它防什么**（只有需求表那一行 + 一处 ✅ 标记）
   —— 「禁符号」很可能是实现时的顺手写法，而非需求本意。

## Decision

**把两条需求与它们的机检判据对齐到「禁常驻，而非禁入口」**（jev `choice` 两轮 0.69 → 0.83，
**未达 0.85 阈值**；本轮由「需求文档自身不一致」这一事实直接判定 —— 见下方判据）。

| 项 | 改后 |
| --- | --- |
| **NFR-3 措辞** | 「文件式：**无数据库、无常驻服务**；运行产物与源码分离」+ 一段边界说明（按需启停的本地入口不属此禁） |
| **NFR-3 判据** | 去掉 `http.server` / `socketserver`；**保留数据库与服务框架**（`sqlite3\|flask\|fastapi\|django\|psycopg\|pymysql\|redis\|\.db`）—— 这才是「文件式」的本体 |
| **FR-16 判据** | ①`daemon\|cron` **只扫代码行**（滤掉注释与 docstring —— 实测 `web.py` 的 docstring 写「不做常驻 daemon」被误命中，把**声明合规**读成**违反**）；②服务启动点必须在 `main` 保护下**可达**（AST 调用传递闭包，而非看行文本） |

**为何这是职责内的修改，而非擅自改需求**：

- 需求文档自称状态是「**需求（待评审）**」——它不是冻结基线，本身就在等发现问题。
- 改的是**需求文档与它自己的机检实现之间的不一致**：措辞说「数据形态」，实现做「符号禁用」。
  这种不一致是**需求文档的内部缺陷**，修它不需要额外授权（改需求**新增/放宽功能承诺**才需要）。
- **功能的取舍早已由用户指令决定**（ADR 0011：用户明确要 web 入口），本篇只解决
  「它与既有需求条款如何共存」。

## Consequences

**已改**：

- `docs/requirements.md`：NFR-3 措辞 + 边界说明。
- `scripts/fr_check.py`：`nfr3_file_based`（黑名单收窄到数据库/框架）、`fr16_no_daemon`
  （AST 可达性 + 代码行过滤）、新增 `_code_hits` 与 `_serve_start_hits`。
- `scripts/goal_check.py`：`n5_no_distributed`（**同一类缺陷的第二处**）—— 它禁 `urllib`，
  而 `urllib` 是标准库的 URL 解析/本机客户端工具，不是「多机分布式调度」。
  改为判**跨主机特征**（`0.0.0.0` / `consul|etcd|zookeeper|celery|rabbitmq|kafka` /
  `socket.create_connection` / `xmlrpc` / `paramiko`），本机 `127.0.0.1` 入口不计。
  **同一类错误在本仓出现了两次**（两个不同的机检脚本把「禁行为」写成「禁符号」）⇒
  这是一类**系统性**缺陷，不是偶发。

**对抗性检验（证明判据没被改松）**：

| 场景 | 判据反应 |
| --- | --- |
| 模块级 `serve_forever()`（真常驻） | ✅ **抓到**（`<module>()` 未被 main 保护） |
| `main() → serve() → serve_forever()`（`web.py` 实际结构） | ✅ 放行（传递闭包正确） |
| 引入 `sqlite3` / `flask` | ✅ 仍抓到（NFR-3 收窄后保留的拦截力） |
| docstring 里写「不做常驻 daemon」 | ✅ 放行（不再把声明读成违反） |
| 植入 `socket.create_connection(("10.0.0.5", 9000))` | ✅ 抓到（非目标5 改后仍拦跨主机） |

**教训（记录，因为这类缺陷会静默复发）**：

1. **「禁符号」很容易与「禁行为」分家** —— 符号是行为的一种表现，不是行为本身。
   写机检判据时要问：**我在判行为还是在判它的一个表征？**
2. **docstring 会被文本判据误命中** —— 文档字符串里写「不做 X」是**声明合规**的常见写法，
   而 `git grep` 读不出这一点。文本判据应至少滤掉注释与 docstring。
3. **判据改动必须做对抗性检验** —— 我第一版 FR-16 判据（看行文本是否含 `if __name__`）
   把合法形态误报为违规；只看直接调用又把合法的传递链误报。**两版都是错的，
   是「拿一个真违规去试」才逼出正确的第三版（AST 可达性）。**
4. **这类缺陷会成批出现** —— 本轮同一类错误在两个脚本里各出现一次
   （`fr_check.py` 的 NFR-3/FR-16、`goal_check.py` 的非目标5），都是「把形态约束
   写成符号黑名单」。**发现一处后，应搜全仓同类判据**（本次已处理二处）。
