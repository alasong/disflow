# 0010 kaa 与 disflow 的融合：只取互补判据，进现有扩展点（不做双引擎）

- **Status**：Active
- **Date**：2026-10-11
- **关联**：[0009](0009-步骤准入-软门槛.md) 判「Spec 调 skill 谁保证准确性」；本篇给出**机制层的落法**。
  参照物：`kaa` skill（`~/.pi/agent/skills/kaa/`，7 道门 + `[forms]` + `events.jsonl`）。

## Context

用户提问（2026-10-11）：「**就我的那个 kaa skill 里面有大量的校验机制和引擎，怎么和这个融合起来？**」

**先看清一件事：两者架构同源**，所以「融合」不是「接两套引擎」：

| 维度 | disflow | kaa |
| --- | --- | --- |
| 事实源 | `events.jsonl` 唯一真相 | `events.jsonl`（`[state].events`） |
| 投影 | `state.json` 可重放 | `state.json`（`write_order` 先事件后投影） |
| 写路径 | `Engine._write` 锁内读→校验→append | `state.exclusive()` + `append_record` |
| 并发 | `store.lock` → `flock` | `flock` 真互斥（1.2 加固） |
| 分发 | `dispatch.drive` 只推不跑 | `runtime.drive` 只推不跑 |
| 多会话隔离 | `DISFLOW_STATE_DIR` | `KAA_STATE_DIR` |
| 门 | `gates.run_acceptance` | `gates.GATES`（7 道） |
| 开工模板 | `context.brief()`（无模板层） | `[forms]` 逐型模板 |

**逐项映射结论：重叠约 60%，互补约 40%。**（⚠️ 此为**人工粗估**，下表是**实测**替代）

**实测对照（`python3` 探针逐个 `hasattr`，13 项 —— 证据优先于估计）**：

| kaa 能力 | disflow 有吗 | 说明 |
| --- | --- | --- |
| 跑验收命令 + 输出匹配 | ✅ | `run_acceptance`（`exit0`/`contains`/`regex`） |
| 改动集归因 | ✅ | `newly_changed`（内容指纹 `baseline` + `base_sha`，**比 kaa 更细**） |
| 作用域门（改动落 `touch_plan`） | ✅ | `scope_check`（≈ kaa 的 `design_first`） |
| 规模预算 | ✅ | `diff_size`（≈ kaa 的 `size_budget`） |
| 空洞通过识别 | ✅ | `vacuous_reasons`（**kaa 无此项**） |
| 树级终止门 / 覆盖门 | ✅ | `tree_closure_check` / `tree_coverage_check` |
| 敷衍理由拒收 | ✅ | **本轮新增**（`weak_reason`，词表） |
| 声称/命令对账 | ✅ | **本轮新增**（`claim_mismatch`，词表） |
| 与树目标词对齐 `goal_align` | ❌ | kaa 有，**未搬** |
| python 代码质量门 `code_quality` | ❌ | kaa 有（裸 `except` / 可变默认参 / `shell=True`），**未搬** |
| 必填声明门 `form_complete` | ❌ | disflow 仅 `acceptance.require_declarations` **近似**，非同一物 |
| 验证真实性门 `verify_real` | ❌ | kaa 有（判假证据，**拒收**）；disflow 仅本轮的**弱版**（对账**信号**，不拒收） |
| `[forms]` / `bus` / `registry` | ❌ | 未搬（理由见下各条） |

**实测结论：9 项有（7 项原有 + 2 项本轮新增）、4 项缺。**

**一条必须写明的判断（防读者高估）**：disflow 的 7 项「原有」**不是从 kaa 来的** ——
两边**本来就都在解同一类问题**（任务树的执行与验收），所以**门名字对得上、概念对得上，但实现各写各的**。
本轮真正搬过来的只有**两个词表 + 一个 `if`**（约 10 行），不是「kaa 的能力都搬来了」。

⚠️ **若不写明这条，读者会把「概念重叠」误读成「能力已具备」** —— 本篇初版就是如此，
用户当场误以为「disflow 现在用了 kaa 的能力」（已纠正）。**文档表述错误会导致真实误判，故记在此。**

| kaa 机制 | disflow 对应 | 判定 |
| --- | --- | --- |
| `events.jsonl` / 投影 / `flock` / 只推不跑 | 同源 | **重叠**（保 disflow 的） |
| `gate_verify_real` / `gate_design_first` / `gate_size_budget` / `gate_form_complete` | `run_acceptance` / `scope_check` / `diff_size` / `require_declarations` | **重叠** |
| `jobs.lease_holder`（按写面查租约） | `dispatch` 的 `touches` + 租约 | **重叠** |
| `registry`（产出物登记） | `assets/registry.json` + `premises` | **重叠**（各管一层） |
| `gate_goal_align`（与树目标词对齐） | 无 | **互补** |
| `gate_code_quality`（py 底线） | 无 | **互补** |
| `weak_reason`（敷衍词表） | 无 | **互补** ← **本轮已落地** |
| `test_claim` 对账（声称 vs 命令） | 无 | **互补** ← **本轮已落地** |
| `[forms]` 逐型开工模板 | `brief()` 是接点 | **互补**（待做） |
| `[state].event_kinds` 双向机检 | 事件闭集在代码里，无声明-发射对账 | **互补**（待做） |
| `bus`（人机通道） | 无（提问走宿主 + `question_protocol`） | **互补但不做**（见下） |

## Decision

**形态 2「声明式融合」**（jev `choice` conf **0.95**；形态1 门插件 0.04、形态3 双引擎 0.0、不做 0.0）：

> **只取互补判据，落进 disflow 现有扩展点（`acceptance` / `brief` / `gates` / 配置键），
> 不搬 kaa 引擎、不建双事实源。**

**两条前置已同一轮判定**（均从事实推出，非假设）：

| 问题 | 答案 | 判据 |
| --- | --- | --- |
| kaa 与 disflow 是什么关系 | **并列**（jev conf **0.98**） | kaa 是 `~/.pi/agent/skills/` 下的独立产品：自有 tag/spec/tests/`events.jsonl`，执行面锚在 fat3 checkout，`loc_hard=4222` 规模预算；disflow 是独立仓、stdlib-only、582+ 用例。**约束不兼容** ⇒ 合并会把 NFR-1（零依赖）与 kaa 的 fat3 依赖撞在一起 |
| 判据以什么形态供给 | **数据**（jev conf **0.97**） | 纯词表类（`weak_reason_blocklist` / `test_claim_words` / `claim_pass_words`）无依赖、无上下文 ⇒ 可直接成为 disflow 配置键；`import kaa.gates` 需适配层且 kaa 住在 skill 目录（非 site-packages），**且会破坏 NFR-1** |

⇒ **接口形态定案：只搬「数据」，不搬「代码」。** 需上下文的门函数（`gate_goal_align` /
`gate_code_quality`）走 `acceptance.cmd` **调命令**这条逃生口，不 import。

**融合准入判据**（两条同时成立才融）：

1. **互补**：它判的是 disflow 现有门**判不到**的东西（不是重复实现）；
2. **落进既有扩展点**：`acceptance` 字段 / `brief` 结构 / `gates` 函数 / 配置键 ——
   **新增事实源一律不融**。

**否掉另两个形态的理由**：

- **形态 3（双引擎编排）**：两份 `events.jsonl` 要同步 ⇒ **重放不一致**，正是
  [0006](0006-spec-一等公民.md) 判死的「第二真相源」；且 `closed`/`awaits` 的跨树信号会变成
  **跨系统**信号，引入分布式共识（FR-23 明确降级为显式完成信号）。**成本高且违背第一纪律。**
- **形态 1（只在 `acceptance.cmd` 里调 kaa 命令）**：可行但太窄 —— 只能整包调用，
  拿不到 kaa spec 驱动的参数，也享受不到「配置键可调」的好处。**保留为逃生口**
  （临时想用某道 kaa 门时，可直接把它写进节点验收命令）。

**`bus` 明确不做**：它是「多人 agent 协作时的人机通道」，而 disflow 是单机「只推不跑」，
提问走宿主通道 + `question_protocol` 已够。判据与 `backlog` §D 一致：
**触发条件（真有 worker 需中途问人且宿主转发不够）不出现就不做。**

## Consequences

**本轮已落地（第一批：纯判据增强，零新实体）**：

| 判据 | 落点 | 行为 |
| --- | --- | --- |
| `gates.weak_reason` | `Engine.done` 的 `no_result` / `scope_waiver` / `size_waiver` | **拒收**敷衍理由；空理由不拦（不越权）；空词表 = 关掉判据 |
| `gates.claim_mismatch` | `Engine.done` 的 `evidence` | **信号**（写进证据，**不参与拒收**）——与 `vacuous_reasons` 同一纪律 |

**配置键**（`disflow.json`，可不写 = 内建默认）：
`weak_reasons` / `test_claim_words` / `claim_pass_words`（逗号分隔或数组；空 = 关掉）。

**待做（第二批，需先设计）**：

- `[forms]` 模板接进 `context.brief()` ⇒ 兑现 [0009] 的「brief 是步骤调 skill 的接点」。
  **前置**：先定 disflow 的「节点型」集合（对应 `role`），否则模板无从分发。
  ⚠️ **第二轮评估（本篇修订）**：这项的可行性受「并列」关系限制 —— kaa 的 `[forms]` 是
  **kaa 自己的 node_type** 模板（implement/research/…），disflow 的 `role` 只有
  dev/qa/pm，两者粒度不同。硬搬会把 kaa 的型集合变成 disflow 的隐含依赖 ⇒
  **应先在 disflow 内定自己的型，再考虑是否复用 kaa 的模板文本**（而不是反过来）。
- `[state].event_kinds` 式**声明-发射双向机检** ⇒ 抓「声明了的事件没人发 / 发了的事件没声明」。
  这是本仓目前**没有**的一类判据（现只在校验层做闭集，无双向对账）。
  **与并列关系兼容**（纯 disflow 内部机制，只是思路借自 kaa）。

**判据**：`tests/test_reason_quality.py`（11 项）钉住两条新判据的**正反两向**
（敷衍词拒收 / 具体理由放行 / 空词表关闭 / 空理由不越权 / 声称与命令对账 / 不凭空报警）。
**测试抓到过真缺陷**：初版实现声称「空词表 = 关掉」但 `len<2` 那条仍拦单字 —— 已修
（实现服从声明，不是反过来）。
