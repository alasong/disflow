# 0009 步骤的准入：软门槛（允许说明性步骤，但必须显式标注「无判据」）

- **Status**：Active
- **Date**：2026-10-11
- **关联**：[0006](0006-spec-一等公民.md) Spec 一等公民（本篇细化它的「步骤」如何准入）；
  [0008](0008-看板不做web化.md) 同属「把边界记录下来，防止反复讨论」。
  机制先例：`disflow/gates.py#vacuous_reasons`。

## Context

用户提问（2026-10-11）：「**Spec 去调 skill 的话，谁来保证它的执行准确性？** 这块我并没有想清楚。」

背景是上一轮讨论的设想：**Spec 写需求+规划+大颗粒步骤+关联资产，步骤去调 skill；skill 按 PDCA 模板写，
承载小步骤/能力；skill 可以调其他方法论/skill**。

**这个问题的实质**：disflow 现有链条上，**每一环都有门，只有一环没有**：

| 环节 | 谁保证 | 判据 |
| --- | --- | --- |
| 任务该不该派 | `ready` / `drive` 波次 | 确定性逻辑 |
| 派给谁 / 写面冲突 | `dispatch` 的 `touches` 重叠检查 | 确定性逻辑 |
| 产出**存在** | `acceptance.cmd`（`exit0`/`contains`/`regex`） | 真跑命令 |
| 改动**在范围内** | `design_first`（改动落 `touch_plan` 内） | git 改动集 |
| 规模**没爆** | `size_budget` | 行数读数 |
| **是否按 brief 的步骤做了** | **无** | ← **缺口** |

**为何是设计使然而非疏漏**：disflow 的非目标是「只推不跑」（FR-16，`backlog` §E）。引擎**看不见
worker 的过程**，只看得到终态（`collect` 结果 + `done` 时的 git 改动集 + 验收命令）。
**过程不可见 ⇒ 过程不可验**，这是「只推不跑」的必然代价，不是可以补的洞。

**「Spec 调 skill」为什么让问题更尖锐**：它把步骤**下放到文本层**（skill 的 PDCA 模板）。
步骤变多了，但**可验的产出没有增加**，反而多了一层「文本契约套文本契约」 ——
链越长，断言越多，**可验比例越低**。最坏形态是「每一步都写了漂亮的 PDCA 模板，但没有一步被真跑过」。

## Decision

**软门槛**（jev `judge` conf **0.98**；硬门槛 0.01、不设门槛 0.0）：

> **步骤的可验性必须显式声明，但不强制所有步骤都可验。**
> 写得出可跑判据的步骤 → 带 `acceptance`（真门）；
> 写不出的 → **允许存在，但必须显式标注「无判据」及理由**，不许 silent 混成普通步骤。

三条判据（为何否掉两端）：

1. **否「硬门槛」（无判据不得登记为步骤）**：会**误伤本就该无判据的节点**。
   本仓 `vacuous_reasons` 已经明确「**空洞不是失败**」—— `evaluate`（收益验证）、`reflect`
   （经验沉淀）这类节点**写面本为空**，本就没有可跑的判据。一刀切会逼人写**恒真判据**
   （`cmd: true`）来绕过，产出**假绿** —— 比无门槛更坏（本仓 `AGENTS.md` 实测：
   「判据写成提示的效力：319 次提及、零行为改变」，而**假判据比没有判据更毒**：
   它让「全过」被读成「都验了」）。
2. **否「不设门槛」（步骤就是文本）**：等于承认执行准确性**无任何保证**，且会让真正有门的那部分
   步骤被**稀释**在无门步骤里 —— 读者无法区分「这条过了」与「这条根本没验」。
3. **取「软门槛」**：与既有 `vacuous_reasons` **同一形状**（记录 + 报出，不拒收、不改变通过结果）
   ⇒ **零新机制、零新概念**，只是把这条纪律从「节点验收」推广到「步骤准入」。

**skill 调 skill 的可验边界**（同一条判据的推论）：

| skill 形态 | 可验性 | 谁能保证准确性 |
| --- | --- | --- |
| 纯文本方法论（如 playbooks 的条目） | ❌ 只能靠人读 | **无人**（只能靠复查） |
| **带可执行入口**（如 `kaa start/done/doctor`） | ✅ 节点的 `acceptance.cmd` 能指到它 | **该 skill 自己的门** |
| 声明式模板（如 kaa 的 `[forms]`） | ✅ 渲染结果可机检（缺键直抛） | 模板渲染器 |

⇒ **「Spec 调 skill」要保证执行准确性，唯一可行形态是：该 skill 有可执行入口，且节点验收命令调它。**
参照物：`kaa` 正是这个形态的成熟实例 —— 它的准确性不来自「PDCA 模板写得漂亮」，
来自 `kaa done` 会**拒收**（门 + 拒收码）。

## Consequences

- **Spec 的「步骤」不新增事实源**（承 [0006] 的硬边界 + 上一轮 jev 裁决 conf 0.91）：
  步骤 = **节点树的投影**，不是 Spec 里另一份独立文本清单。每个步骤的门就是**该节点的 `acceptance`**。
- **落点（将来实现时的判据）**：`disflow` 侧把 `vacuous_reasons` 的同类信号推广到节点声明层 ——
  节点可**显式标注**「本步骤无判据」；`board` / `brief` 呈现时与有判据的步骤**分色/分标**，
  使「全过」与「都验了」在任何视图上都不可混淆。
- **`brief()` 是「步骤调 skill」的接点**（`context.py:19`，返回结构化 dict，已有 `context`/
  `acceptance`/`touch_plan` 字段）：若将来要让节点声明它用哪个 skill，**加字段即可，不新设实体**。
- **不改变任何现有门的通过/拒收行为** —— 与 `vacuous_reasons` 同款：只记录、只呈现。
- **非目标重申**：不用 PDCA 模板去「保证」执行准确性。模板是**指令面**，门才是**保证面**；
  把模板当保证 = 用文本约束替代门，已被本仓实测否掉。
