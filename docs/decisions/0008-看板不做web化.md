# 0008 看板不做 web 化（形态判据：web 的增量价值只在多人/远程/图形化）

- **Status**：**Superseded by 0011**（2026-10-11 同日：用户明确要求 web 入口，本 ADR 的「不做」裁决被推翻；
  **保留的价值**：它记下了「何时才值得做」的触发条件清单与形态排序 A/B/C —— 0011 直接沿用那份形态序）
- **Supersedes（部分）**：——（本篇无）
- **Date**：2026-10-11
- **关联**：[0005](0005-看板提升为一等实体.md) 把看板升为一等实体；本篇裁决**它的渲染层不做 web**。
  与 `backlog` §E「明确不做」同一条纪律：把「不做什么」也记录在案，防止反复讨论。

## Context

用户提问（2026-10-11）：「现在我的看板机制能不能把它实体化，比如说把它设计 web，把它展示出来？
**适合做么**」——问的是**该不该**，不是「我要一个 web 看板」。

**能力上完全可行**，逐层核对过源码：

| 层 | 现状 | 对 web 的含义 |
| --- | --- | --- |
| 事实源 | `events.jsonl` 唯一真相，`state.json` 可重放 | 无需为 web 新增存储 |
| 看板结构 | 板定义随 `tree.init`/`tree.boards` 进事件流、投影携带（§6.1） | 板有身份、可重放 |
| 渲染 | `views.board_layout()` 返回**结构化 dict**（columns→groups→rows，带 `parent`/`depth`/`group`/`done`/`total`）；`board --json` 是它的直接序列化（`cli.cmd_board`） | **web 要的机读契约已存在**，`tests/test_views.py` 已钉住 |
| 纯读 | `board` 跑前后 `events.jsonl`/`state.json` **逐字节不变**，`tests/test_cli_readonly.py` 钉住 | 只读 HTTP 端点安全，不污染真相 |
| 实时层 | 宿主 `lanes_watch.py` 已 join 看板 `--json` + pi 运行目录，复用成品行 | 「在场看进度」已被覆盖 |

**缺的不是能力，是需求**：web 相对于现状的**增量价值只在三件事**上——①多人协作（别人也要看）、
②远程访问（不在本机）、③图形化（波次/依赖图这类列视图表达不了的形态）。三者都需要**先有真实需求**才成立。

## Decision

**本轮不做 web 化**（jev `choice` conf **0.97**，C_do_nothing 概率 0.98；收窄问题前后两次都是 C，
补事实后从 0.83 收敛到 0.97）。

判据不是「web 不好」，是三条：

1. **增量价值的三根支柱（多人/远程/图形化）一根都未出现** ⇒ 做了就是 `backlog` D4「动态看板」的重演
   ——那个功能的**触发条件至今未出现**，是**按指令做的投机功能**。项目纪律（`backlog` §D）
   要求「触发条件出现才做」，同一条判据适用于此。
2. **最便宜的形态也不该现在做**：引擎零改动、`board --json` 已是完备契约，任何前端只需消费它。
   正因为**以后做的成本很低（随时可补）**，现在就没必要先做 —— 低成本的另一面是**低紧迫**。
3. **已有替代物**：`board`（在场人读）+ `board --json`（机器消费）+ `lanes_watch.py`（在场实时）
   + `--by board`（四块板流程视图）已覆盖单机自用的全部真实场景。

**形态排序**（若将来触发条件出现，按此顺序取最低成本者）：

| 形态 | 何时取 | 成本 | 约束 |
| --- | --- | --- | --- |
| **A** 静态 HTML 消费 `board --json`（`file://` 或 `python3 -m http.server`） | **默认首选**：只要「比命令行好看一点的图形」 | 约半天，**引擎零改动** | 保持 NFR-1：不引入构建链/前端框架 |
| **B** 只读 HTTP 服务（`http.server` + 前端轮询） | A 不够，且确实需要**远程/多人只读** | 1–2 天，多一层常驻进程与刷新节拍 | 只读；端点包 `board --json`，不新写投影 |
| **C** 带写操作的服务（网页上派发/验收） | 仅当有**多人协作编辑**的真实需求 | 高 | ⚠️ 会打破「纯读」优势与会话级租约模型，须单独 ADR 重议 |

**结构性非目标**（重申 `backlog` §E）：常驻 daemon、WebSocket、前端框架、多机分布式调度。

## Consequences

- **不新增任何代码**；引擎、视图、CLI 一字不改。
- **触发条件（将来重启此议的判据）**：出现以下**任一事实**时，回到本 ADR 取形态 A：
  ①有本机之外的人需要看这棵树；②需要同时看多棵树/多树波次的图形化总览；
  ③命令行 `board` 的列视图已不足以表达工作流程（如需要依赖图/甘特）。
  **仅「想实体化」「想好看点」不构成触发条件** —— 那正是本 ADR 要挡住的重复讨论。
- 本仓据此维持：**看板的实体化 = 数据层已完成的既成事实**（ADR 0005），**渲染层 = 终端 + 纯文本行序**
  （`views.board_rows` 为唯一行序来源）。web 只是将来**可能追加的第三种渲染**，不改变任何现有契约。

## 后续（2026-10-11 同日，**追加不改原文**）

**本篇的「不做」已被推翻 —— 但推翻它的不是新论据，是用户指令。**

用户同日明确要求：「我需要一个入口来下发任务。在 Web 上同时把资产也展示一下。」
即 **【③ + 用户意志】** 同时到位：不是「想好看点」这种空想，是**明确的功能要求**。

本篇的哪些部分**仍然有效**（被 0011 沿用）：

- **形态排序 A/B/C**（静态页 → 只读服务 → 带写操作）—— 0011 直接在这份序上选。
- **结构性非目标**（常驻 daemon / WebSocket / 前端框架 / 多机分布式）—— 0011 继续遵守。
- **「引擎零改动、`board --json` 即契约」** —— 0011 的实现证实了这一点：web 层只消费
  `views.board_layout`，一行分列/分组逻辑都没重写。

本篇判断**错在哪**（诚实记录）：它把「没有人要求」当成「需求不存在」，而**用户的指令本身就是需求事实**。
更准的表述应是「无触发条件时不应**主动**建 web」——这与「用户要求时应建」不矛盾。
