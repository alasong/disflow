# 0014 本质与未来形态：四个不可动原子 + 一条替换判据

- **Status**：Active
- **Date**：2026-10-13
- **关联**：[0003](0003-运行视图-v10-按板列不按树.md)（视图同源）、[0005](0005-看板提升为一等实体.md)（板是一等实体）、
  [0006](0006-spec-一等公民.md)（Spec 一等公民）、[0008](0008-看板不做web化.md) / [0011](0011-web入口-实现.md)（入口形态）、
  [0010](0010-kaa融合-声明式.md)（不做双引擎）
- **判据来源**：`jev choice` conf **0.88**（问题：是否新增单一落点篇；A=0.92 > C=0.08）

## Context

用户连续两次追问同一件事（2026-10-13）：

1. 「人类组织搞那么多项目管理、看板和任务看板，是为了什么？**从 AI 的角度看，这个是为了啥？**」
2. 「整这么多的**最根本的目的是什么**？帮我整理一下，抽出其中的关键东西。」
3. 「你觉得最后的解决方案是什么？**面向未来的方案**又是什么？」

**问题本身是信号**：同一结论被反复需要，说明它此前**没有单一落点** —— 四个原子与未来形态的判断
散落在 0003 / 0005 / 0006 / 0008 / 0010 / 0011 各自的 Context 里，每次都要重新拼。

同时，用户提出了一个真实的分叉：「**我也可以不搞多个看板，用树把这个任务列表管理起来**。」
这需要一条**可复用的判据**来裁决，而不是每次口头论证。

## Decision

### 1. 本质：四个不可动原子

一切形态（板 / 树 / 图 / web / CLI）都只是这四个原子的**显化**。

| # | 原子 | 实现落点 | 删掉的后果 |
| --- | --- | --- | --- |
| A1 | **状态外部化**（不靠记忆，靠事件流；可重放） | `events.jsonl` 唯一真相 / `state.json` 是投影 | 退化成「只能靠人盯的 TODO」 |
| A2 | **就绪判据化**（「该不该做」是计算，不是判断） | `ready(n)` 唯一函数 | LLM 参与「该不该拿」，不可复现、不可 dry-run |
| A3 | **完成可判定**（必须有命令证据） | 门 + `baseline`→`introduced` 归因 + 写面校验 | LLM 说「完成」即完成 —— 最容易被骗的一环 |
| A4 | **上下文投影**（靠注入不靠继承） | `brief(n)` fresh-context | 上下文漂移 / 污染，并发不可能 |

### 2. 判据：新东西是「消费」还是「复制」已有判据

**面向未来，任何改动只问一句**：

> 这个新东西，是在**消费**已有判据，还是在**复制**已有判据？

| 类别 | 例子 | 裁决 |
| --- | --- | --- |
| **消费**（新的投影消费者 / 新的策略宿主 / 新的入口） | 新的看板渲染、web 端点、Spec 关联资产 | **做**（成本低，ADR 0011 是范例：薄壳只转发） |
| **复制**（另写一套判据 / 第二份存储） | 第二份 `state.json`、另一套就绪判定、另一套看板布局 | **不做**（ADR 0003 原话：「同一判据两份实现 ⇒ 两面分叉」） |

**这条判据取代逐个论证**：以后遇到「要不要加 X」，不必回溯六个 ADR，直接分类即可。

### 3. 直接回答「能不能只用树管理任务列表」

**能，但砍掉的是渲染与策略宿主，砍不掉判据。** 三句分清：

| 概念 | 表达什么 | 能否被树替代 |
| --- | --- | --- |
| 树 | `parent` 层级 = **归属**（谁属于谁）+ 作用域隔离 + 上下文继承 | —— |
| 看板列 | 阶段 = **处于哪一步**（running / pending / done） | **不能**：阶段不是父子关系；用树硬编码阶段 ⇒ 改阶段即改树 |
| 板级策略 | WIP 逐列上限、逐列默认验收（FR-30/31） | **不能**：无板则策略只能散回每个节点，即 ADR 0005 明确否决的旧形态（「规则挂在板上，不散落在每个节点上」） |
| 板 | 「**空也在**」的固定结构（用户 2026-10-11 原话：像墙上钉的一块板子） | **不能**：树是长出来的，板是钉住的 |

**代价核算**：砍到单树列表，省的是「板实体 + 列持久化 + 逐列策略」的代码；
付出的是把阶段语义压进树的形状、策略散回节点。**这是当时有意选的形态，不是堆出来的**（ADR 0005 Context）。

### 4. 未来方案：引擎不变，实体补齐，入口增厚

| 阶段 | 内容 | 触发条件（`docs/v0.2-backlog.md` 已登记） |
| --- | --- | --- |
| 近 | **Spec 升为引擎级实体**（FR-33；ADR 0006 已定模型，当前仅资产层可用） | 「真要用 Spec 管从资产上新到交付且需事件流/重放」——**无触发即不做** |
| 中 | **板持有全部策略**（WIP / 逐列验收已有；FR-32 动态看板已有逐树覆盖） | 出现第二种流程形态时 |
| 远 | **入口泛化**：每个新入口都遵守 ADR 0011 判据（薄壳，不重写判据） | 出现第二个入口时 |
| **永不做** | 双引擎（ADR 0010）、常驻 daemon、WebSocket、前端框架（ADR 0008 结构性非目标，0011 未推翻） | —— |

## Consequences

- **单一落点**：本质与未来形态从「散在六个 ADR 的 Context」收敛到本篇；后续再被问，直接指这篇。
- **不改实现**：本篇是**对既有裁决的收口**，不新开机制、不改代码、不改需求基线。
- **不新增需求**：FR/NFR 不动；`scripts/fr_check.py` / `goal_check.py` 无需同步。
- **登记**：本篇**必须**进 `docs/INDEX.md` 与 `docs/decisions/README.md` 索引表，否则
  `tests/test_docs_index.py` 红（纪律：不登记 = 永不被读到）。
- **已知局限**：第 3 节「能不能只用树」的结论是**论证性**的（依据 ADR 0005 的既有裁决），
  没有代码读数；若真要砍板，需先给出「策略新宿主」的方案，那时再开新篇。
