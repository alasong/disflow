# 0006 Spec 升为一等公民（独立实体；关联资产而非归属）

- **Status**：Active
- **Date**：2026-10-11
- **关联**：[0005](0005-看板提升为一等实体.md) 把**看板**升为一等实体；本篇把 **Spec（交付单元）**
  升为一等实体，并厘清它与资产的关系。

## Context

用户要「**通过 Spec 管理任务，从资产上新到交付的整个过程**」，含三件：①资产**上新**（onboarding）、
②功能的**全量交付**（不止文档与需求，还有代码）、③**Spec 自身也是资产**。

现状与冲突：

- 本仓「Spec」一词**多义**：`disflow/spec.py` 的 `SPEC`（机制常量）、节点 `acceptance`（节点验收点）、
  flowcore 实例 spec。`assets/README.md` 曾把 spec 定位为「**节点验收点**，最多管门」。
- **项目资产**（`assets/registry.json`，`premises` 依据 DAG）与 disflow 的 `tree.assets`（任务产出物）
  是**两层且明确不接**。
- 资产是**跨交付可复用**的（一份设计/文档可被多个交付单元引用）。

用户裁决（2026-10-11）：Spec 升为一等公民；**Spec 关联资产，而不是把资产挂到它下面**。

## Decision

**Spec 是独立的一等实体**（jev `choice` conf **1.0**）：

| 维度 | 决定 |
| --- | --- |
| **身份** | 独立 `id` + `goal` + **完成判据（gate）** + 状态；独立生命周期；随事件流持久化、可重放 |
| **层级** | **独立顶层实体**——不是节点的字段、不是树的别名（「节点升格」「树粒度」均被否：一等公民要独立身份；自身要能登记为资产；跨交付可复用） |
| **与资产** | **关联**（`Spec → 资产`，**多对多**、可带类型）：资产独立存在，不因 Spec 而生灭——**无 `asset.parent = spec`** |
| **交付清单** | Spec 声明它交付的**角色清单**（requirement / design / implementation / verification / documentation）；「全量交付」= 角色齐全 |
| **自身** | Spec **也是资产**（可复用记录，进同一登记，带 `tier`/`premises`） |

**关联 vs 归属 的判据**（为何选关联）：

- 归属（containment）：`asset.parent = spec`，1:N，删 Spec 资产随灭 ⇒ 与「资产可复用、可被多个交付单元引用」**矛盾**。
- 关联（reference）：`spec.assets = [...]`，M:N，资产独立 ⇒ 与可复用一致。

## Consequences

- **硬边界（不是第二真相源）**：Spec **不**定义资产刷新**顺序**（顺序派生自 `premises` 拓扑序，
  见 `assets/README.md`）；**不**复制 tree/node 的状态与就绪判定（那属 disflow 引擎）——Spec 只声明
  「交付什么（角色清单）+ 算不算完成（gate）+ 关联哪些资产」。
- **需求基线**：`docs/requirements.md` 新增 **FR-33**（Spec 一等公民）、**FR-34**（Spec 关联资产，
  非归属）；§7 标 **未实现**。
- **资产模型**：`assets/README.md` 增「Spec 与资产：关联」一节。
- **目标设计**：`docs/design-dispatch-tree-graph.md` 增 Spec 实体草案（标注未实现）。
- **待实现**：Spec 实体 + 关联边 + 交付清单门（本轮只落**模型与需求**，未落代码）。
