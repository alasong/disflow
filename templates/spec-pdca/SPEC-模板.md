## P · 计划

> 这一段的栏目**取自 OpenSpec 的 proposal / spec / design / tasks**（`spec-driven` schema），
> 按 PDCA 收进一个 P 段。改动它们之前先看那四个模板的定义，别凭感觉加删。

### P1 为什么做（Why）

<1–2 句：解决什么问题 / 为什么是现在。>

### P2 要什么（What Changes）

<具体说新增/修改/删除什么。**破坏性变更用 `**BREAKING**` 标出来**。>

- <例：新增 `POST /api/v1/users`>
- <例：**BREAKING** 登录响应体去掉 `token_type`>

#### P2.1 影响哪些既有能力

| 类型 | 能力 | 怎么变 |
| --- | --- | --- |
| 新增 | <例：user-auth> | <这个能力覆盖什么行为> |
| 修改 | <例：user-profile> | <哪条既有需求在变——**只列需求级变化，纯实现调整不列**> |

> **为什么单列这张表**：它逼你想「这事会不会动到别处」。
> 只写「做什么」，很容易漏掉对既有行为的破坏。
>
> **纯重构 / 工具 / 文档**（不改变对外行为）→ 写「无能力变化」，别硬造一条需求。

#### P2.2 影响面（Impact）

<受影响的代码、API、依赖、系统。>

### P3 需求场景（**每条都要能测**）

> **这是本模板最值钱的一段。** 需求不写成场景，AI 就会自己猜边界。
> 格式取自 OpenSpec 的 delta spec：`Requirement` + `Scenario` + **WHEN/THEN**。
>
> 三条硬规矩（OpenSpec 原文的约束，照抄）：
> ① 规范语言用 **SHALL / MUST**，不用 should / may；
> ② **每条 Requirement 至少一个 Scenario**；
> ③ 场景用 `####`（**四个** `#`）—— 层级错了会被静默忽略。

### 需求：<需求名>

<一到两句说清这个需求。一条需求只说**一个**行为——多个行为就拆成多条需求。>

#### 场景：<场景名>

- **WHEN** <条件>
- **THEN** <期望结果>

#### 场景：<另一个场景（边界 / 异常）>

- **WHEN** <例：邮箱已存在>
- **THEN** <例：返回 409，错误码 `EMAIL_ALREADY_EXISTS`>

> **边界要写全**，否则 AI 自己定：空值 / 越界 / 并发 / 无权限 / 重复。
>
> **可验 vs 不可验**：
> ✅「重复邮箱返回 409」「密码用 Argon2id 哈希」「P95 < 200ms」
> ❌「保证安全」「性能要好」「代码优雅」

### P4 怎么做（How）

> 只在**需要**时写（OpenSpec 的条件）：跨模块改动 / 新架构模式 / 新外部依赖 /
> 数据模型大改 / 安全·性能·迁移有复杂度。**简单的改动跳过这段。**

#### P4.1 上下文（Context）

<当前状态与约束。**动机见 P1，此处不重复**；需求见 P3，也不重复。>

#### P4.2 目标 / 非目标（Goals / Non-Goals）

**目标**：

- <这个设计要达成什么>

**非目标**（显式排除，防范围漂移）：

- <例：这期不做找回密码>

#### P4.3 关键决定（Decisions）

| 决定 | 选了什么 | 为什么 | **被否的替代方案** |
| --- | --- | --- | --- |
| <决策点> | <例：PostgreSQL> | <理由> | <例：MySQL——被否因为…> |

> **「被否的替代方案」这一栏别省**：不写，下次有人会重新提同一个方案，
> 而那次的讨论记录已经找不到了。

#### P4.4 风险 / 取舍（Risks / Trade-offs）

<格式：`[风险] → [缓解]`>

- <例：新增索引使写入变慢 → 只在低峰期建，且用 `CONCURRENTLY`>

#### P4.5 遗留问题（Open Questions）

<**只放"可以安全延后"的未知**。如果这个问题会改变需求/方案/任务拆解，
那它**不是遗留问题**——现在就问清楚，别把假设埋进任务里。>

### P5 任务（每条**自带怎么验**）

| # | 任务 | 怎么验（**写在任务里**，别堆到最后一组） |
| --- | --- | --- |
| 1.1 | <一个能独立验收的小单元> | <命令 / 测试 / 可观察行为> |
| 1.2 | | |

> **两条硬规矩**（OpenSpec 原文）：
> ① **每个任务组自己带上该组的测试与文档** —— 别收集到最后一组。
> 最后一组只做**集成检查**，不补前面欠的测试。
> ② **粒度**：一个小会话能做完。太粗（"完成用户模块"）会漏东西；
> 太细（"加个 email 字段"）维护成本超过收益。

## C · 检查

> **OpenSpec 缺这一段**（它的 `verify` 是**可选 profile**，不在核心五步里）。
> 这里把它做成**必填**：没有命令与输出，就等于没检查。

## 附：与 disflow 的对应（可选）

`P5 任务` 的每行直接映射成一个节点：

```bash
disflow init <功能名> --goal "<P1 的 Why>"
disflow expand <功能名> root --children '[
  {"id":"t1","goal":"<任务描述>",
   "acceptance":{"cmd":"<C1 的命令>","expect":"exit0"},
   "touch_plan":["<会改的文件>"]}
]'
disflow host-next <功能名>
```

`done` 时引擎会**真跑** `acceptance.cmd` 并**自算**证据（改动归因用内容指纹），
`C1` 段就是这些证据的存档。

**注意**：`touch_plan` 要写**文件**路径——写目录可能触发写面重叠判定。
