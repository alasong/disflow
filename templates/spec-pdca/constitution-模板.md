# 项目铁律（constitution）

> **这份文件不随功能变**——它是所有 spec 的**共同前提**。
> 填一次，之后很少动；动一次要回头看所有功能是否还合规。
>
> **判据**：这条规则，**换到别的仓库还成立吗**？
> 成立 → 那是通用常识，不用写（AI 本来就会）。
> 不成立 → **写进来**（这才是你项目的特有约束）。
>
> 另一条判据：**AI 猜错了我能立刻发现吗？** 不能 → 要么写成可验的形式，要么删掉。

## 3. 红线（AI **绝对不许**碰）

> **注意**：写在这里只是**影响生成倾向，拦不住**。
> 真正要拦的规则得推进到 **pre-commit hook / CI**（见文末）。

- 🚫 <例：不得连生产库>
- 🚫 <例：不得提交密钥（`.env` 不进版本库）>
- 🚫 <例：不得删线上数据>
- 🚫 <例：不得改已发布的 API 路径>

## 4. 需要先问的操作（⚠️ Ask first）

> **刚开工宁严勿松**：多放几条，跑一段时间后把每次都对的操作降到「自动」。
> 规则必须**具体**——「重要变更需确认」AI 没法执行，它不知道什么算重要。

- ⚠️ <例：修改已有 API 的 URL 路径 → 先出方案等审>
- ⚠️ <例：ALTER TABLE / 加索引 → 先出方案等审>
- ⚠️ <例：新增第三方依赖 → 先说明为什么标准库不够>

## 7. 这份铁律怎么维护

| 时机 | 动作 |
| --- | --- |
| 建项目 | 填一次（第 1–6 节） |
| Code Review 发现同类问题**第 2 次** | 回来加一条 |
| 红线被绕过 | 别只加文字——**加到 pre-commit / CI** |
| 半年没看 | 逐条问「还成立吗」，过期的删掉（过期的规则比没有更坏） |

**红线不是靠自觉的**，多层防线（越重要的越要靠后）：

```text
① 写在这里          → 影响生成倾向，拦不住
② 配置模板          → `.env.example` 里不放真实值，就没东西可复制
③ pre-commit hook   → 正则扫密钥硬编码 / 生产连接串
④ CI                → 越重要的规则越要落到这一层
⑤ 凭据隔离          → 生产凭据不落在可访问的工作区，用短期最小权限
```

**停在「文档里有写」，迟早出事。**
